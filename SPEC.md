## 0. Summary

Build a production-style **email scheduler service + dashboard**:

- Users log in with **Google OAuth**.
- They compose an email, upload a recipient list (CSV/TXT), and schedule it with a **start time**, a **delay between emails** and an **hourly limit**.
- The backend stores everything in **Postgres**, schedules sends with **BullMQ delayed jobs on Redis** (no cron anywhere), and sends through **Ethereal SMTP** using multiple senders.
- It survives restarts, never double-sends, enforces per-sender hourly limits across workers, and posts a **real Slack message** when a limit is hit.
- Emails are indexed in **Elasticsearch** and searchable. A **Bull Board** dashboard shows the queue live.

### Hard constraints (non-negotiable)

1. **No cron.** No `crontab`, `node-cron`, `agenda`, or anything similar. BullMQ delayed jobs only.
2. **Persistent.** After a restart, future emails still send on time and nothing is re-sent or restarted.
3. **Idempotent.** The same email must never be sent twice.
4. **Rate-limit state lives in Redis (or the DB), never in memory.** It must be safe with multiple workers or instances.
5. When the hourly limit is hit, jobs are **delayed to the next window, never dropped or failed.**
6. All limits and concurrency values are **configurable via env**, never hardcoded.

## 4. Data Model (Prisma)

```
User
  id (uuid, pk) | googleId (unique) | email (unique) | name | avatarUrl | createdAt

Sender                        # Ethereal SMTP accounts, several per user
  id | userId -> User | email | smtpHost | smtpPort | smtpUser | smtpPass | createdAt

Campaign                      # one compose/schedule action
  id | userId | senderId | subject | bodyHtml | startAt | delaySeconds | hourlyLimit | total | createdAt

Email                         # one row per recipient
  id (uuid, pk)
  campaignId -> Campaign | userId | senderId
  toEmail | subject | bodyHtml
  scheduledAt (timestamptz)   # updated if the email is pushed to a later hour window
  status: scheduled | sending | sent | failed
  sentAt (nullable) | attempts (int, default 0) | error (nullable)
  messageId (nullable) | previewUrl (nullable)     # Ethereal preview link
  jobId (unique)              # = "email:<id>", the idempotency key
  createdAt | updatedAt
  indexes: (userId, status, scheduledAt), (senderId, status)

SlackConnection
  id | userId (unique) -> User | teamName | channelName | webhookUrl | createdAt
```

Seed script: create **2 or more Ethereal senders** via `nodemailer.createTestAccount()` and store them. Also expose `POST /api/senders/ethereal` to create one on demand.

## 5. Backend Requirements

### 5.1 Scheduling flow

`POST /api/emails/schedule`

1. Validate the body (zod). Normalize, lowercase and **dedupe** recipients and drop invalid ones.
2. In **one DB transaction**, create the `Campaign` and one `Email` row per recipient with `status=scheduled` and `jobId="email:<id>"`.
3. Compute each email's `scheduledAt`:
   `scheduledAt[i] = max(startAt, now) + i * delaySeconds`
   (`startAt` null means send now.)
4. Enqueue to BullMQ with **`queue.addBulk` in chunks of ~500**, with `{ jobId, delay: scheduledAt - now, attempts: 3, backoff: exponential, removeOnComplete: { age: 3600 }, removeOnFail: false }`. The job payload contains only the `emailId`. The worker reads everything else from the DB.
5. Index each email in Elasticsearch (bulk).
6. Respond `201 { campaignId, total, firstScheduledAt, lastScheduledAt }`.

### 5.2 Worker (`src/worker.ts`)

BullMQ `Worker` with:

- `concurrency: WORKER_CONCURRENCY`
- `limiter: { max: 1, duration: MIN_SEND_DELAY_MS }`, the **minimum delay between sends** (documented in the README, default 2 s)

Per job, in order:

1. **Atomic claim (idempotency):**
   `UPDATE "Email" SET status='sending', attempts=attempts+1 WHERE id=$1 AND status='scheduled' RETURNING *`
   If 0 rows come back, the email was already sent or claimed, so **return without sending**. Also allow reclaiming a row stuck in `sending` for more than 2 minutes (crash recovery).
2. **Hourly rate-limit check** (section 5.3). If over the limit, reschedule (do not send).
3. Send through `nodemailer` using the email's sender SMTP config.
4. On success: `status='sent'`, `sentAt`, `messageId`, `previewUrl` (`nodemailer.getTestMessageUrl`), then update the ES doc.
5. On error: throw so BullMQ retries with backoff. After the final attempt, set `status='failed'` with `error`, and update the ES doc.

### 5.3 Hourly rate limiting (per sender, Redis, multi-worker safe)

- Key: `rate:{senderId}:{hourWindowStartEpoch}` with TTL of about 2 hours.
- A **Lua script** does an atomic `INCR` and sets `EXPIRE` on first creation, returning the new count. The limit is `campaign.hourlyLimit`, falling back to `MAX_EMAILS_PER_HOUR_PER_SENDER`.
- If `count <= limit`: proceed to send.
- If `count > limit`:
  - Do **not** fail or drop the job.
  - `overflowIndex = count - limit - 1`
  - `newTime = nextHourWindowStart + overflowIndex * MIN_SEND_DELAY_MS`
  - Move the job back to delayed with `job.moveToDelayed(newTime, token)` and `throw new DelayedError()` (BullMQ's mechanism for rescheduling without consuming an attempt).
  - Set the Email row back to `status='scheduled'` with the new `scheduledAt`, and update the ES doc.
  - Because overflow jobs get increasing offsets, **order is preserved as far as possible**.
  - Trigger the Slack notification (section 5.6).
- Document the trade-offs in the README: fixed window vs sliding window, and that the limiter counts attempts at the window boundary.

### 5.4 Behavior under load (1000+ emails at the same time)

- Enqueueing uses chunked `addBulk`, so a 1000+ recipient request is fast and the API does not block.
- Delayed jobs sit in Redis. Only `WORKER_CONCURRENCY` jobs run at once, and the BullMQ limiter spaces sends by `MIN_SEND_DELAY_MS`.
- When a sender's hourly limit is exceeded, the overflow is pushed to the next window(s) with preserved ordering. Nothing is lost.
- The README must describe this explicitly and ideally include a short load-test script (`scripts/load-test.ts`) that schedules 1000 emails with a low `hourlyLimit` and prints the resulting distribution per hour window.

### 5.5 Restart persistence

- Postgres is the source of truth for email state. Redis holds the delayed jobs (AOF persistence on).
- **Boot-time reconciliation** (runs when the worker starts): find `Email` rows with `status='scheduled'` that have no matching job in the queue (`queue.getJob(jobId)` returns null) and re-enqueue them with the **same `jobId`** (a no-op if it already exists, so there is no duplication). Also reset stale `sending` rows (older than 2 minutes) back to `scheduled`.
- Demo: schedule emails 2 minutes out, kill the API and worker, restart them, and the emails still go out on time exactly once.

### 5.6 Slack notification on rate-limit hit

- `GET /api/slack/connect` (authenticated) redirects to Slack's OAuth authorize URL (`scope=incoming-webhook`, signed `state` containing the userId).
- `GET /api/slack/callback` exchanges the code at `oauth.v2.access`, then stores `incoming_webhook.url`, team name and channel in `SlackConnection` (upsert per user).
- `GET /api/slack/status` returns `{ connected, teamName, channelName }`.
- `DELETE /api/slack/disconnect` deletes the row.
- When a sender's limit is hit, look up the **owner's** `SlackConnection`:
  - If none exists, skip silently (no crash, no error).
  - If one exists, POST a message to the webhook, e.g. "Rate limit reached for sender X (N/hour). Remaining emails rescheduled to HH:MM."
  - **Debounce:** only notify once per sender per hour window (`SET slack:notified:{senderId}:{window} NX EX 3600`).
  - Wrap in try/catch. A Slack failure must never break the worker.
- Reconnecting works without a redeploy because the webhook is read from the DB at hit time.
- Slack needs an https redirect URL, so use **ngrok** locally (set `BACKEND_URL` and `SLACK_REDIRECT_URI` to it).

### 5.7 Elasticsearch

- Index `emails` with fields: `id, userId, toEmail, subject, body (text), status, scheduledAt, sentAt, senderEmail, campaignId`.
- Create the index with mappings on startup if it is missing.
- Index on schedule. Update on every status change (sent, failed, rescheduled).
- Search is exposed through `GET /api/emails?q=...` (section 6). Match on `toEmail`, `subject` and `body` with `multi_match`, filtered by `userId` (and `status` when given).
- If ES is down, the API must **still work** for non-search queries, and indexing failures are logged and never block sending.

### 5.8 Bull Board

- Mount `@bull-board/express` at `/admin/queues`.
- Protect it with basic auth using an env pair (`BULL_BOARD_USER` / `BULL_BOARD_PASS`) or at minimum an authenticated session.

### 5.9 Auth (Google OAuth)

- `GET /api/auth/google` redirects to Google.
- `GET /api/auth/google/callback` exchanges the code, upserts the `User` (googleId, email, name, avatar), sets an httpOnly JWT cookie, and redirects to `FRONTEND_URL/scheduled`.
- `GET /api/auth/me` returns `{ id, name, email, avatarUrl }` (401 if not logged in).
- `POST /api/auth/logout` clears the cookie.
- CORS: `origin = FRONTEND_URL`, `credentials: true`. All `/api/*` routes except `/api/auth/*` require auth.

## 6. REST API Contract (the frontend codes against this)

All responses are JSON. Errors have the shape `{ "error": "message" }` with a proper HTTP status. Times are ISO-8601 UTC strings.

### Types

```ts
type EmailStatus = "scheduled" | "sending" | "sent" | "failed";

interface Email {
  id: string;
  to: string;
  subject: string;
  bodyPreview: string;      // plain text, first ~120 chars
  bodyHtml: string;
  status: EmailStatus;
  scheduledAt: string;
  sentAt: string | null;
  senderEmail: string;
  error: string | null;
  previewUrl: string | null; // Ethereal preview link
}

interface Paginated<T> { items: T[]; total: number; page: number; limit: number; }
interface Sender { id: string; email: string; }
interface Me { id: string; name: string; email: string; avatarUrl: string; }
```

### Endpoints

| Method | Path | Notes |
|---|---|---|
| GET | `/api/auth/google` | Starts login (browser redirect) |
| GET | `/api/auth/me` | → `Me` |
| POST | `/api/auth/logout` | → `{ ok: true }` |
| GET | `/api/emails?status=scheduled\|sent&page=1&limit=20&q=` | → `Paginated<Email>`. `status=sent` returns both `sent` and `failed`. `scheduled` also includes `sending`. `q` triggers Elasticsearch search. |
| GET | `/api/emails/counts` | → `{ scheduled: number, sent: number }` (sidebar badges) |
| GET | `/api/emails/:id` | → `Email` |
| POST | `/api/emails/schedule` | Body below → `201 { campaignId, total, firstScheduledAt, lastScheduledAt }` |
| GET | `/api/senders` | → `Sender[]` |

| GET | `/api/slack/status` | → `{ connected: boolean, teamName?: string, channelName?: string }` |
| DELETE | `/api/slack/disconnect` | → `{ ok: true }` |

**Schedule request body**

```json
{
  "senderId": "uuid",
  "subject": "string (required)",
  "bodyHtml": "string (required)",
  "recipients": ["a@x.com", "b@y.com"],
  "startAt": "2026-10-07T10:00:00.000Z",
  "delaySeconds": 5,
  "hourlyLimit": 100
}
```

Rules: `startAt` is optional (null or missing means now). `delaySeconds >= 0`. `hourlyLimit >= 1`. At least one valid recipient. Max recipients per request: 5000.
